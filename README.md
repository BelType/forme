# forme

forme is a PDF 2.0 writer for Caster, BelType's printer, written in Rust. In letterpress the forme is the type locked into its frame, ready for the press, which is what a display list becomes when it is written. Caster measures the page in the browser and hands its writer one plain value, the display list; forme takes that list and writes the file. It is built to replace Caster's TypeScript writer, the oracle, which writes through pdf-lib and HarfBuzz's subsetter, and it runs in two places from one crate: in the tab as a WebAssembly module Caster vendors, and on the machine as the `forme` binary. It writes the document's scaffolding, every font instance the list names, subset and instanced by subsetter with the `hmtx` held to the list's widths, each page's marked content and text, its pen tracked as the oracle tracks it, the structure tree, and every image: a JPEG or a PNG passed through under the filter that reads it, the photo rule's JPEG, and samples deflated with an `/SMask` where a pixel is not opaque, the rectangles, and the colour story: the output intent with its CMYK profile, `/DefaultRGB` on every page, spot inks as `/Separation` spaces, overprint graphics states, the black-text policy and the print marks in `/All`, and the vector items: paths with every paint and stroke attribute, clips and transforms, axial and radial shadings over stitched functions, patterns for gradient strokes, constant alpha, blend modes and soft masks in shared graphics states, isolated groups and soft masks as transparency-group forms, forms written once and drawn many times, and raster fallbacks, and the facsimile, a page of another PDF copied in as a Form XObject. It decodes no image, since the page decodes before the list what no filter reads, and converts no colour. It refuses by name the one item kind it does not write, the dormant colour cluster.

## What it reads

forme reads the display list of version 6, as Caster's `src/displayList.ts` defines it, and nothing else: no page, no measurement, no clock. The list arrives as the JSON `JSON.stringify` makes of it without `resources.blobs`, and the blobs arrive beside it, each named by its SHA-256. On the machine that is Caster's fixture format, a `<name>.json` beside a `blobs/` folder. `src/list.rs` is the schema on the Rust side, read by forme's own JSON reader in `src/read.rs` (no serde is linked), and names the sharp edges JSON hides: offsets in UTF-16 code units, numbers parsed exactly, JavaScript's rounding, the four arrays whose order is data. `src/validate.rs` refuses what Caster's `validateList` refuses, with the same sentences in the same order.

## The gate it is held to

forme is held to the readers, not to the oracle's bytes (*the same list prints the same bytes*, Caster's DESIGN.md S102). On every list committed in Caster's `fixtures/lists/`, the readers ask the same questions of the oracle's file and of forme's: whether every parser opens it, whether the validator agrees, whether the same list gives the same file, and later the records, the content streams, the tree, the words, the fonts, the images and the pixels. Each stage of the round adds the readers its writing needs, and the plan names them stage by stage (`.claude/plans/the-rust-writer/plan-rust-writer.md`, in the BelType monorepo). forme writes four things the oracle does not, each named: the trailer `/ID`, a CFF2 face, font programs without hinting tables, and later the Well-Tagged PDF declarations.

## How to build and test

Run `cargo build` for the library and the binary, then `cargo test` with a Caster checkout as the sibling `../caster`, or name it in `CASTER`; the tests read its committed lists. Run `forme validate <list.json>` to hold one list to the validator, and `forme write <list.json> --blobs <dir> -o <out.pdf> [--records <out.json>]` to write its file and, with `--records`, the writer's records as Caster's `WriterRecords` JSON, which Caster's `npm run identity -- compare <dir>` reads beside the file. Build the module with `RUSTFLAGS="--remap-path-prefix=$HOME/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f=crates --remap-path-prefix=$PWD=forme" cargo rustc --lib --profile wasm --target wasm32-unknown-unknown --crate-type cdylib` from the checkout, then shrink it with `wasm-opt -Oz --enable-bulk-memory --enable-nontrapping-float-to-int`. Without the two flags `wasm-opt` refuses the module, because rustc 1.99 emits both features. The two prefixes are crates.io's source folder and the checkout: without them the module carries the builder's home directory in about seventy panic locations, and with them it is about 4 kB smaller (the standard library's own locations, under `/rustc/<commit>`, come prebuilt and stay). The crate type is named because cargo performs no LTO on a library whose crate types include `rlib`, and this one has both, for the tests and the binary; `cargo build --lib` builds the module without LTO. In the module the API is one class, `Writer` (`src/wasm.rs`, wasm-bindgen 0.2.129): `new Writer()`, `writer.blob(key, bytes)` once per blob, then `writer.write(listJson)`, which returns `{ bytes, records }` or throws the refusal's sentence as an `Error`, with `listItem` where it names an item. Caster's `scripts/bundle-forme.js` builds it by this recipe, runs `wasm-bindgen --target web` on it before `wasm-opt`, and vendors the glue and the module. The module's size, glue included, is held to the bytes it lets Caster delete, 1 061 704. The tests turn on the crate's `serde` feature, through forme's dev-dependency on itself, to write a list back through serde's `Serialize` and to read the oracle's JSON with serde_json (1.0.154, `float_roundtrip`); the module and the binary `cargo build` makes never link serde. `NOTICE` carries the notices of the code subsetter adapts, which travel with every binary.
